# Offline dependency closure and compilation input locks

Implemented 2026-09-20. Policies: `explicit-directory-closure-v1` and
`compilation-input-lock-v1`. This extends explicit PE/CIL compilation, not a
NuGet restore engine, CLR assembly loader, signature verifier or security sandbox.

## CLI workflow

```sh
dotnet build Transpiler.slnx -c Release
CLI=src/Transpiler.Cli/bin/Release/net10.0/Transpiler.Cli.dll

# Discover the application implementation graph only in these directories.
dotnet "$CLI" compile App.dll --target js --out app.mjs \
  --reference-dir vendor/first --reference-dir vendor/second \
  --write-input-lock app.inputs.json --manifest app.manifest.json

# Subsequent builds verify identities, actual bytes and compiler configuration.
dotnet "$CLI" compile App.dll --target js --out app.mjs \
  --reference-dir vendor/second --reference-dir vendor/first \
  --input-lock app.inputs.json --manifest app.manifest.json
```

`--reference-dir` is repeatable. Supplying it enables full application dependency
closure, including metadata-only dependencies that may not be reachable from an
export. Without it, the previous explicit `--reference` behavior is retained.
For C# input, source binding still requires the relevant `--reference` arguments;
closure runs after Roslyn has emitted the real root PE. Emitting PE first makes
this separation explicit. `--reference-dir` is accepted by compile/analyze;
input locks apply to compile only. Record and verify flags are mutually exclusive.

An executable, two-library sample is in `samples/input-locks/`. Run
`python3 samples/input-locks/build.py` after building the compiler. It generates
both targets, records locks, relocates the assemblies, verifies the same locks,
compares generated bytes, and runs both outputs. No network access or package
restore is performed by the resolver or sample driver.

## Resolution algorithm and policy

The root and explicit implementation references seed a work queue. Assembly
headers are inspected through PE metadata without decoding candidate method
bodies. Each AssemblyRef is resolved once per requesting assembly. Cycles
terminate through the identity-indexed visited map. Exact identity means the
name, version, culture and public-key token represented by the existing
`AssemblyIdentity` model; this is not lossless CLI signature identity.

Existing explicit inputs take precedence, but a mismatching explicit identity
is an error, never a reason to search for a replacement. Otherwise the resolver
checks `<simple-name>.dll` and `<simple-name>.exe` in every explicit directory.
There is no recursive scan and no implicit search of the working directory,
root assembly directory, SDK implementation directories or NuGet caches. Unsafe
simple names are rejected before constructing candidate paths.

Matching byte-identical copies are equivalent, independent of directory order.
Matching identities with different SHA-256 content are ambiguous and rejected.
A different version or reference-only assembly cannot satisfy the request. A
malformed candidate with the requested filename fails closed, even when another
directory contains a usable candidate. Unrelated files are not inspected.

Selected images are imported from their existing snapshots and passed into the
normal linker, forwarding resolver, library substitution and specialization
pipeline. ExportedType forwarding adds ordinary dependency edges and is covered
by an unchanged-consumer test. New closure logic does not implement binding
redirects, framework-facade expansion, multiple versions per simple name, or
multiple load contexts.

The existing reviewed framework-name list, a neutral culture and one of the
recognized framework public-key tokens identify external framework contracts.
Those references are recorded, not automatically loaded as implementation IL.
Framework versions are not certified by a full framework loader policy. A
framework-like name with an unrecognized token is not silently exempted from
application dependency resolution. Tokens identify keys; this feature does not
verify strong-name signatures or authenticate a binary's publisher.

`dependencyBindings` in the provenance manifest records requester identity,
requested identity, implementation/framework-contract kind, and implementation
SHA-256 where applicable. No absolute candidate path is needed to replay a
locked graph from a different checkout location.

## Snapshot consistency

A `CompilationInputSession` owns immutable file snapshots for one compilation.
The same bytes are used for fingerprinting, candidate identity inspection,
Roslyn metadata references and implementation import. A later filesystem write
cannot change an already-captured input. Creating another session sees the new
file. The cache uses normalized absolute paths with host-appropriate case
comparison; it is not an inode cache or a realpath-based filesystem sandbox.

The session is single-owner and is not intended to be shared between parallel
compilations. Source text is decoded from its captured image. In-memory callers
remain responsible for the source text/root model they construct themselves.
No file snapshot API can make multiple externally changing files one atomic
filesystem transaction; the lock verifies the particular set of captured bytes.

## Lock contents and verification

A schema-1 lock contains normalized target, dispatch mode, BCL policy, managed
input identities and SHA-256 values, reference-pack fingerprints when used, and
seven selected compiler/toolchain fingerprints: CLI, core, frontend, backend,
Roslyn common/C# assemblies and the running CoreLib. The graph's root PE and
portable/original library implementation images participate in managed inputs.
For C# input, the reference pack captured during source binding is retained.

Locks contain no absolute paths, timestamps, output destinations, search-path
ordering or machine names. Quota settings are not semantic input identity.
Relocating byte-identical inputs and reordering equivalent reference directories
therefore leaves the lock valid. Rebuilding the compiler, changing Roslyn or the
host CoreLib, changing target/dispatch/BCL policy, or replacing an input image
requires deliberate lock regeneration. This is byte-identity replay, not a
promise that independently rebuilt compiler distributions have identical bytes.

All expected/current input sets are compared. Extra, missing or changed inputs
fail with `TR3311`, listing bounded, section-specific differences. JSON with
unknown/duplicate properties, invalid hashes, duplicate identities, missing
sections or unsupported schema/policy fails with `TR3310`. Array ordering in a
valid lock does not change its meaning. The manifest records the canonical
lock digest and whether verification was requested.

Verification completes before target emission and output writes. A rejected
replay does not install new code and does not delete a pre-existing output.
Output and sidecar collisions with explicit or snapshotted inputs are rejected;
diagnostics do not overwrite an already-captured dependency on a failing path.
As before, target and sidecar files are individually replaced, not one atomic
multi-file transaction. Check exit status before consuming existing outputs.

A lock is not itself a package store or a dependency download instruction. The
caller must provide the root and authorized paths containing the matching
bytes. Locks do not pin every OS/environment setting or every transitive host
runtime dependency, and do not imply authentication, signatures, full hermetic
build isolation or cross-module runtime object identity.

## Budgets and cooperative cancellation

Defaults are 128 MiB per file, 512 MiB total file bytes and 4,096 captured files.
Override them with `--max-input-bytes`, `--max-total-input-bytes` and
`--max-input-files`. Positive decimal values are required. Per-file bytes cannot
exceed Int32-sized images. Cached reads do not spend the same bytes twice;
distinct paths, including inspected candidates, consume budget. File size is
checked before allocation and incrementally while reading, so growth during a
read cannot bypass the byte limits.

The resolver additionally bounds reference directories to 256 and reference
edges to 16,384. The existing 256-assembly linker limit still applies, including
framework/portable images added by the selected library policy. No directories
are silently dropped to meet a limit.

Embedding code can supply a CancellationToken through the session and compiler
phase APIs. The CLI handles Ctrl+C cooperatively and exits 130 with `TR0003`.
Checks occur at file chunks, metadata/type/method and resolver work queues,
Roslyn parsing/emission, specialization rounds, analysis methods, SSA methods
and emitted-method boundaries. These are not preemptive CPU deadlines: a single
expensive parser, verifier or native-emitter operation may finish before the
next checkpoint. C++ emission is canceled at the surrounding phase boundaries.

```csharp
using Transpiler.Core;
using Transpiler.Frontend.Roslyn;
using Transpiler.Backends;

static GeneratedSource Compile(string rootPath, string[] directories,
    CancellationToken cancellationToken)
{
    var inputs = new CompilationInputSession(
        new CompilationInputLimits(MaxFileBytes: 64L << 20,
            MaxTotalBytes: 256L << 20, MaxFiles: 512), cancellationToken);
    var root = AssemblyImporter.Read(inputs.Read(rootPath).Content.ToArray(),
        cancellationToken: cancellationToken);
    var linked = PortableCompilation.Link(root, [],
        new LinkOptions { ReferenceDirectories = directories }, inputs);
    var analyzed = CompilerAnalysis.Analyze(linked, cancellationToken);
    return SourceEmitter.Emit(analyzed, SourceTarget.JavaScript,
        new SourceEmissionOptions(DispatchMode.StackSsa), cancellationToken);
}
```

Optional cancellation/session parameters preserve source call patterns. Existing
binary consumers should rebuild against the updated compiler assemblies.

## Diagnostics and evidence

| Code | Meaning |
|---|---|
| TR3030 | Candidate metadata cannot be inspected |
| TR3031 | Exact implementation missing; observed mismatches/reference-only candidates are reported |
| TR3032 | Same identity has multiple byte-distinct implementations |
| TR3033 | Unsafe simple name for filesystem probing |
| TR3034 | Reference edge/directory budget exceeded |
| TR3300 | File count, per-file or total input-byte quota exceeded |
| TR3310 | Malformed or unsupported input lock |
| TR3311 | Lock options or fingerprint sets differ |
| TR0003 | Cooperative compilation cancellation |

Existing TR3000/3001/3002/3003 diagnostics continue to identify assembly-budget,
reference-only input, conflicting explicit inputs and identity mismatch cases.
The new tests include 52 direct snapshot/lock/closure/cancellation invariants,
both targets' real cyclic assembly graphs, ordinary/SSA relocated replay,
reference/content/version conflicts, forwarded consumers, source/BCL lock
replay, changed reference/toolchain fingerprints, and output-preservation paths.
The independent input-contracts CI job supplements the unfiltered suite.

Primary API references: [PEReader](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.portableexecutable.pereader),
[AssemblyReferences](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata.metadatareader.assemblyreferences),
and [AssemblyReference identity fields](https://learn.microsoft.com/en-us/dotnet/api/system.reflection.metadata.assemblyreference).
PEReader is not an untrusted-input isolation boundary. Use process isolation,
OS quotas and a watchdog for hostile inputs; bounded file reads do not establish
full metadata-verifier safety.
